# 工作室共用架構 v1

## 共用的是交付能力，各遊戲保留自己的玩法

每款遊戲一個專案、一個獨立 App 身分與版本歷史。`studio.project.json` 記錄執行產物、語言、驗證命令、平台與發布授權；`AGENTS.md` 記錄專案例外；`HANDOFF.md` 只記目前事實與下一步。使用者提出新想法後，由代理完成初始設定，毋須使用者反覆描述這些工作習慣。

小型 2D 離線遊戲先以 HTML Canvas 原型驗證操作與趣味；這是預設選項，不強迫 3D、重物理或大型內容遊戲沿用。新遊戲若需要其他引擎，先比較手機性能、資產流程、包體與維護成本，再記錄選擇理由。GOO BLASTER 保留單檔產物，不在本次移植引擎。

邏輯上的共用分界：

| 區域 | 合約 | 驗證重點 |
|---|---|---|
| 遊戲規則 | 狀態更新、關卡、傷害、經濟 | 可重播種子、真正勝負、新手與滿級配裝 |
| 顯示與輸入 | 繪圖、觸控、鍵鼠、聲音 | 真實點擊／觸控、窄螢幕、音訊停止與恢復 |
| 平台服務 | 存檔、圖片匯出、生命週期、離線 | Web／Android 各自的實際落地效果 |
| 發行 | 版本、封裝、簽章、測試入口 | 產物內容、身分與簽章、公開下載校驗 |

平台服務的結果必須能表達 `success`、`cancelled`、`unavailable`、`error`；UI 不得把「已呼叫函式」當作「已存檔」。原生細節留在外殼，遊戲呼叫能力介面並提供本地化回饋。第一次複用原生程式時移除舊遊戲的命名與身分；不要複製私鑰或舊進度。

## 開發節奏

想法 → 一頁遊戲簡報 → 可玩的最小迴圈 → 手機操作／性能 → 內容與難度 → 語言與上架素材 → 測試通道 → 正式送審。

每次只完成可驗證的一項行為或一個平衡槓桿，保留前後比較。先修功能失效再調整難度；不把機器人勝率當真人勝率。缺少母語潤稿就明示。付費模式預設一次買斷、無廣告／付費隨機機制；售價與受眾每款分別確認，不能沿用前作定價。法律、商店規範與市場資訊在需要時查官方現行資料，不把這份文件当法律結論。

## 多 agents 的使用標準

現在不需要常駐多 agents。當有两項互不依賴的實質工作、界線清楚且預期節省時間時，先說明工作範圍與額外成本，再依專案授權啟用。建議最多先試 2 個：主代理實作；另一個只負責獨立稽核或指定測試檔。具備足夠內容量後才考慮翻譯或商店素材代理。

每個任務指定輸入、允許改的檔案、驗收證據與返回格式；禁止另一個代理同時修改共用 index.html／字典產物。主代理負責整合及完整驗證。工作樹可隔離程式碼，但不能隔離同一台電腦的 CPU；效能測試必須獨占測試時段。

## 驗證與發布

驗證分成原始碼、瀏覽器執行、原生產物、實機四層。不能把任一層的成功代替另一層。新專案剛初始化时沒有遊戲與測試，工具必須回報「未就緒」，不能產生假綠燈。

每款有自己的固定手機測試頁；先確認新專案的儲存庫、測試分發授權與簽章建立方式，再啟用。測試更新與正式商店上架是兩種授權。更新保持相同 appId／簽章，版本碼遞增，下載後核對實際內容；不要求玩家刪除遊戲來處理升版錯誤。測試回報只需版本、關卡、遇到的現象；影片與存檔由使用者自願提供，不增加預設追蹤／帳號／雲端成本。

共用流程版本與遊戲版本分開。更新工作室 skill 不應自動覆寫每個專案；先看該專案差異，再遷移可用部分。這一版建立規則、初始化與設定檢查；各引擎的實作、測試、商店素材及送審仍要按遊戲完成。
